======================== (JVM):
В виртуальной машине Java, память делится на несколько областей для хранения данных во время выполнения программы. Некоторые области общие для всей JVM, другие создаются отдельно для каждого потока. К основным областям памяти в JVM относятся стек, куча и область методов. Также в Java есть концепция прямого доступа к памяти (direct memory). 
------------------------ (Stack):
область памяти, где хранятся локальные переменные и информация о вызовах методов. Для каждого потока выделяется свой стек. Некоторые особенности стека:
--	Работает по принципу LIFO (Last In, First Out), то есть последний добавленный элемент будет первым извлечённым. 
--	Когда поток вызывает метод, на стек добавляется новый стековый фрейм, а когда метод завершает выполнение, соответствующий стековый фрейм удаляется из стека. 
--	Переменные внутри стека существуют только пока запущен метод, который их создал. 
--	Если память стека заполнена, Java выдаёт исключение java.lang.StackOverflowError. 
--	Стек потокобезопасен, поскольку каждый поток работает в своём собственном стеке.

------------------------ (Heap):
область памяти, где хранятся объекты и массивы, созданные в процессе выполнения программы. Некоторые особенности кучи: Делится на две области: молодое поколение (Young Generation) и старое поколение (Old Generation). 
----	Young Generation состоит из трёх частей: одной области Eden и двух областей Survivor Space (S0 и S1). Все новые объекты сначала создаются в области Eden, после процесса сборки мусора выжившие объекты перемещаются между областями Survivor Space.

----	Old Generation предназначено для хранения объектов, которые прожили достаточно долго и не были удалены во время предыдущих процессов сборки мусора. Объекты из молодого поколения могут быть перемещены в старое поколение, если они продолжают существовать после нескольких сборок мусора. 
proselyte.net
Особенности heap:
-Когда эта область памяти полностью заполняется, Java бросает java.lang.OutOfMemoryError.
-Доступ к heap медленнее, чем к stack.
-Heap, в отличие от стека, автоматически не освобождается — для сбора неиспользуемых объектов используется сборщик мусора Garbage Collector.

------------------------ (Metaspace):
область памяти в виртуальной машине Java (JVM), где хранятся метаданные классов и другая статическая информация приложения. Заменила область PermGen (Permanent Generation) в Java 8 и более поздних версиях. Metaspace хранит, например:
Метаданные классов 		—информацию о структуре классов (имена классов, имена полей, имена методов, модификаторы доступа).
Пул констант 			—набор значений, используемых в байт-коде, включая числовые константы, ссылки на классы и методы, строковые литералы.
Статические переменные 		—переменные, которые связаны с классом, а не с его экземплярами. Имеют одно значение для всех экземпляров класса и сохраняют своё значение между вызовами методов.
Код методов 			—скомпилированный байт-код для методов класса.
Принцип работы Metaspace:
Управлять размером Metaspace можно с помощью флагов JVM: 
-XX:MetaspaceSize 		—устанавливает начальный размер Metaspace.
-XX:MaxMetaspaceSize 		—задаёт максимальный размер, до которого может расти Metaspace.
По умолчанию Metaspace увеличивается автоматически и не имеет явного ограничения. Без установленного ограничения размер Metaspace неявно ограничен объёмом системной памяти хоста. 
Параметры Metaspace:
Если Metaspace превышает свой размер, приложение может столкнуться с ошибкой java.lang.OutOfMemoryError: Metaspace. Это обычно происходит, когда приложение динамически генерирует и загружает большое количество классов или когда размер Metaspace не правильно настроен для требований приложения. Для устранения ошибки можно попробовать:
Увеличить размер Metaspace с помощью флага -XX:MaxMetaspaceSize.
Проверить код приложения на наличие проблем, которые вызывают чрезмерную загрузку классов (например, ненужную динамическую генерацию классов или загрузку классов в цикле).

========================== УТЕЧКА ПАМЯТИ:
-проблема, когда объекты, которые больше не нужны приложению, продолжают храниться в памяти, поскольку на них есть ссылки в других местах. В результате (Garbage Collector) сборщик мусора не может очистить это пространство. Признаки утечки памяти:
-снижение производительности приложения;
-увеличение потребления памяти с течением времени без соответствующего увеличения нагрузки на приложение;
-частые действия по сборке мусора;
-исключения OutOfMemoryError — признак того, что в приложении заканчивается память, вероятно, из-за утечки памяти.
--Объекты не отпущены после того, как перестали быть нужны;
--Объекты потерявшиеся в Collections, например HashMap;
--Внутренние классы используются, а внешние нет, ео ссылка на них сохраняется;
--Не закрытые Connections к Data Base;
--ПРоблемы в native методах. Native-методы в Java — это методы, реализация которых находится не в Java-коде, а в нативной библиотеке. Ключевое слово native — модификатор метода, указывающий компилятору, что реализация находится на другом языке программирования, например на C или C++.  Для взаимодействия с нативным кодом в Java используется Java Native Interface (JNI) — программный фреймворк, который позволяет Java-коду взаимодействовать с нативными приложениями и библиотеками. 
-------------------------- (Thread):
в Java — это отдельная линия выполнения внутри программы. Потоки работают параллельно, разделяют общую память и могут обращаться к одним и тем же данным. При этом у каждого потока есть свой stack и свои локальные переменные, поэтому он может выполнять задачи независимо от других. За работу с потоками в Java отвечает класс Thread.
-------------------------- Автоматическое управление памятью Java:
см. картинку "Memory cleaning"

Мусор		-это объекты, на которые не осталось ссылок.
========================== Garbage collector:
В Java существует несколько алгоритмов сборки мусора, каждый из которых оптимизирован для определённых сценариев использования. Некоторые из них: 
Serial GC 			—однопоточный сборщик, останавливает выполнение приложения во время сборки мусора. Прост и эффективен для небольших приложений и устройств с ограниченными ресурсами. «stop-the-world» пауза.
Parallel GC 			—многопоточный сборщик, использует несколько threads-потоков для сборки мусора, значительно сокращая время пауз по сравнению с Serial GC. Оптимизирован для максимальной пропускной способности, но всё ещё вызывает полные «stop-the-world» паузы.
Concurrent Mark-Sweep (CMS) 	—одновременная разметка, -разработан для минимизации пауз за счёт выполнения большей части работы параллельно с приложением. Используется в приложениях, где важно низкое время отклика. Основной недостаток — фрагментация памяти при длительной работе.
Garbage-First (G1) 		—гибридный сборщик, заменивший CMS в качестве стандартного в Java 9. Разделяет кучу на регионы фиксированного размера и фокусируется сначала на регионах с наибольшим количеством мусора (отсюда название «Garbage-First»).
-------------------------- Reference counting:
один из подходов к реализации Garbage Collector (сборщика мусора) в Java. Суть подхода — подсчёт ссылок на объекты. Принцип работы:
Каждый объект в программе имеет счётчик ссылок: 
1/	Когда создаётся новый объект, его счётчик ссылок устанавливается в 1.
2/	Каждый раз, когда объект используется, его счётчик ссылок увеличивается на 1.
3/	Когда объект больше не нужен, его счётчик ссылок уменьшается на 1.
4/	Когда счётчик ссылок становится равным нулю, объект удаляется из памяти.
Особенности:
	:Подход прост, не требует долгих пауз для сборки мусора.
	:Каждый раз, когда объект используется (например, присваивается переменной или полю, передаётся методу), счётчик увеличивается на 1.
	:Когда ссылка на объект уничтожается (метод возвращается, переменная выходит из области видимости и т. д.), счётчик уменьшается на 1.
Проблемы и некоторые недостатки подхода Reference counting:
--Сложность обеспечения точности счётчика. 
--Сложность выявлять циклические зависимости — когда два объекта больше не используются, но каждый из них ссылается на другой. Это приводит к утечкам памяти: такую память невозможно освободить и выделить под другие объекты. 
--Влияние на производительность — каждый раз, когда объект используется (например, записывается ссылка на объект в локальную переменную), нужно увеличивать счётчик. 
--Проблема с многопоточностью — обновление счётчиков ссылок должно быть атомарным, так как они обновляются несколькими потоками. 
-------------------------- Mark and Sweep:
алгоритм сборки мусора (Garbage Collector, GC) в Java, который состоит из двух этапов. 
Mark (маркировка): 		-GC сканирует все объекты и помечает «живые» (объекты, которые всё ещё используются). На этом этапе выполнение программы приостанавливается, поэтому этап также называется «Stop the World». GC проходит по дереву объектов, начиная с определённых объектов (корней) и следуя ссылкам от них к другим объектам. Каждый объект, который посещает GC, помечается как «живой». 
Sweep (очистка): 		-Освобождается память, занятая объектами, не отмеченными на предыдущем этапе. Все объекты, для которых значение метки равно «false», удаляются из памяти кучи, для всех других (достижимых) — «true». 
Преимущества:
	+алгоритм обрабатывает циклические ссылки, не заходя в бесконечный цикл;
	+не требует дополнительных затрат на выполнение.
Недостатки Mark and Sweep:
--долго, потому что Heap содержит миллионы объектов;
--во время работы алгоритма выполнение программы приостанавливается. Необходжимо выполнить Stop-the-World (STW) — пауза, которая возникает во время этапа mark. В это время все потоки приложения в JVM приостановлены, но приложение внутри об этом не подозревает. Продолжительность STW-паузы зависит от многих факторов: объёма используемой памяти в куче, количества живых объектов, сложности графа объектов и других. В крупных производственных приложениях эти паузы могут длиться от десятков миллисекунд до нескольких МИНУТ;
--высокая фрагметрация памяти. После нескольких запусков Mark and Sweep «живые» объекты могут быть разделены на множество небольших неиспользуемых регионов памяти. Также при -большом количестве «живых» объектов работа алгоритма становится менее эффективной.
-------------------------- Mark-Sweep-Compact:
алгоритм сборки мусора (Garbage Collector, GC) в Java, который состоит из трёх этапов: маркировки, очистки и уплотнения. 
Mark (маркировка):		—GC сканирует все объекты и помечает живые (объекты, которые всё ещё используются). На этом этапе выполнение программы приостанавливается.
Sweep (очистка):		—освобождается память, занятая объектами, не отмеченными на предыдущем шаге.
Compact (уплотнение):		—объекты, пережившие очистку, перемещаются в единый непрерывный блок памяти. Это уменьшает фрагментацию кучи и позволяет проще и быстрее размещать новые объекты.
Используется в разных сборщиках мусора, например: 
Serial GC 	— для очистки старого поколения, для молодого — алгоритм Mark-Copy.
Parallel GC 	— работает по тому же принципу, но для фаз маркировки и уплотнения используются несколько параллельных потоков.
CMS 		— использует алгоритм Mark-Sweep, уплотнение выполняется только в крайнем случае, если система не может выделить объект из-за недостаточного непрерывного пространства. В поздних версиях Java CMS не используется.
Принцип работы:
Для оптимизации сборки мусора память кучи дополнительно разделена на области в зависимости от возраста объектов: 
	Young Generation	—это область памяти для новых, вновь создаваемых объектов, а 
		Eden 	—одна из трёх областей Young Generation. Область, где изначально выделяются все новые объекты. Когда создаётся объект, JVM сначала пытается выделить память в Eden: если в этой области достаточно свободного места, объект помещается туда.
		S0(1) 	—первое из ВЫЖИВШИХ-"Survivor Spaces". В начале сборки мусора одно из "Survivor Spaces" — "To space"пустое, а другое "From space" содержит объекты, пережившие предыдущие сборки;
		S1(2) 	—второе из ВЫЖИВШИХ-"Survivor Spaces". В начале сборки мусора одно из "Survivor Spaces" — "To space"пустое, а другое "From space" содержит объекты, пережившие предыдущие сборки;
	Old Generation		—здесь хранятся давно живущие объекты. Их перекладывать никуда не будем. Объекты с высокой степенью вероятности пригодятся.
В многопоточном приложении используется механизм TLAB (Thread-Local Allocation Buffers), который для каждого потока выделяет определённую область памяти. Параметры и некоторые флаги, которые можно использовать для настройки процесса сборки мусора:
	-Xms 				— первоначальный размер кучи.
	-Xmx 				— максимальный размер кучи.
	-XX:NewRatio=n 			— отношение размера Old Generation к Young Generation.
	-XX:SurvivorRatio=n 		— отношение размера Eden к Survivor.
	-XX:MaxTenuringThreshold=n 	— возраст объекта, когда объект перемещается из области Survivor в область Old Generation.
-------------------------- Mark-Copy, Sweep и Compact:
Эти подходы отличаются подходом к освобождению памяти и перемещению объектов. 
Mark-Copy 				—вариация алгоритма Mark-Sweep-Compact. Вместо удаления мёртвых объектов алгоритм копирует живые объекты в новую область кучи. Старая область кучи при этом считается пустой и может использоваться для будущих выделений. 
Особенности:
	:Маркировка и копирование происходят во время этапа маркировки — живые объекты копируются по мере их обнаружения.
	:Весь цикл сборки мусора может происходить за один проход по графу объектов, что делает этот подход подходящим для редко заполненных куч.
Недостаток: 
--для работы алгоритма требуется отдельная дополнительная область памяти — «to-space», которая должна быть достаточно большой, чтобы вместить выжившие объекты.
