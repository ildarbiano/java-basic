================================ Архитектура:
Архитектура — это один из самых важных начальных этапов любого проекта.
Представим, что перед нами стоит задача построить дом. Конечно, мы начнём с того, что выясним его размеры, материалы и место постройки. Изучим местность, подготовим чертежи и проекты. Точно так же важно соблюдать процессы стройки, использовать качественные материалы, не нарушать основных принципов. Такой подход не даст в результате получить непригодный для жилья дом, который развалится через пару лет. В написании кода всё точно так же. Тут тоже важно соблюдать технологические процессы, качественно относиться к проектированию и т.д. А ещё важную роль играет необходимость гибкости написанного кода. Потребности бизнеса меняются, какие технологии. Поэтому задача в том, чтобы всегда была возможность поддержки и развития проекта минимальными средствами. Проблемы с архитектурным решением «сегодня» приводит нас к ряду проблем «завтра», например:
Плохая масштабируемость кода 			(минимальные запросы на изменение или расширение функционала ведут к огромным временным затратам).
Сильная связность кода 				(изменение всего одной частички кода влечёт за собой изменения в огромном количестве мест).
Сложность в поддержке 				(с внедрением новой функциональности растёт количество проблем и ошибок, что приводит к невозможности поддержки).
Все эти проблемы ведут к одному: переписывать код становится проще, чем поддерживать старый. Если сравнить с домом, то представьте: вы недавно заселились в новый дом, а у него уже течёт крыша. Починить её нельзя, потому что она сильно связана со стенами. И вот вам построить новый дом уже намного проще и дешевле, чем ремонтировать старый. Более того, если вы решитесь на изменения старого, то может выясниться, что он для этого не готов, так как изначальная архитектура сильно «хромает».
Важно понимать: 				переписать код с нуля или построить заново дом не страшно, если это делается ради глобального расширения или из-за сильного скачка технологий. Но в архитектуру нужно закладывать усилия для спокойного поддержания и развития в дальнейшем. В архитектуре есть множество разветвлений для изучения, но мы начнём с самых простых, которые отвечают за стиль написания кода и проектирования классов и методов.
В программировании существует свод принципов — SOLID.
-------------------------------- SOLID это набор принципов:
-------------------------------- SINGLE responsibility:
Принцип единственной ответственности. Single responsibility principle. Для каждого класса должно быть определено единственное назначение. Все ресурсы, необходимые для его осуществления, должны быть инкапсулированы в этот класс и подчинены только этой задаче.
-------------------------------- OPEN–closed:
Принцип открытости/закрытости. Open-closed principle. Программные сущности должны быть открыты для расширения, но закрыты для модификации.
-------------------------------- Liskov substitution:
Принцип подстановки Лисков. Liskov substitution principle. Функции, которые используют базовый тип, должны иметь возможность использовать подтипы базового типа, не зная об этом.
-------------------------------- INTERFACE segregation:
Принцип разделения интерфейса. Interface segregation principle. Много интерфейсов, специально предназначенных для клиентов, лучше, чем один интерфейс общего назначения.
-------------------------------- DEPENDENCY inversion:
Принцип инверсии зависимостей. Dependency inversion principle. Зависимость на Абстракциях. Нет зависимости на что-то конкретное.
Все эти принципы ведут нас в мир чистой и красивой разработки. Остановимся более детально на первом, рассмотрим пример.
public class CarService {					//Класс, который отвечает за взаимодействие с машиной:
   public void checkEngine() {
       //проверить двигатель
   }
   public void startEngine() {
       //завести двигатель
   }
   public void checkSafetySystem() {
       //проверка системы безопасности авто
   }
   public void lightsOn() {
       //влючить свет
   }
   public void lightsOff() {
       //выключить свет
   }
}
Мы имеем методы для работы с некоторыми ключевыми функциями автомобиля и их может быть намного больше (в десятки, сотни и тысячи раз). И нехорошо, что эти функции лежат в одном общем сервисе и не имеют своего модульного класса, который ими управляет. Ведь в разных методах идёт взаимодействие с разными модулями (в нашем случае это модуль двигателя, безопасности и освещения). Получается, что такой огромный класс будет невозможно прочитать за адекватное количество времени. К тому же, этот сервис сильно связан. Если начнутся проблемы в одном из модулей, с которыми он работает, упадёт весь сервис.
В данном случае лучше всего разбить один большой сервис на множество небольших, отвечающих за определенный модуль автомобиля:
public class EngineService {
   public void checkEngine() {
       //проверить двигатель
   }
   public void startEngine() {
       //завести двигатель
   }
}

public class SafetyService {
   public void checkSafetySystem() {
       //проверка системы безопасности авто
   }
}

public class LightService {
   public void lightsOn() {
       //влючить свет
   }
   public void lightsOff() {
       //выключить свет
   }
}
Это не означает, что CarService не будет существовать. Он будет делать, что и должен, при соблюдении принципа единственной ответственности. Например, управлять всеми модулями.
================================ Reflection API:
Рефлексия — это механизм, который даёт разработчику возможность получать и изменять информацию о классах, интерфейсах, методах и полях во время выполнения, не зная при этом их имён. Reflection API может создавать новые экземпляры классов, изменять или получать значения их полей и вызывать методы. Используется практически во всех современных технологиях Java и лежит в основании большинства современных фреймворков и библиотек.
Например, в:
Spring 		—фреймворков для создания веб-приложений,
JUnit 		—фреймворк для тестирования.
Некоторые из возможностей рефлексии:
+	Узнать класс объекта.
+	Получить информацию о модификаторах класса, методах, полях и конструкторах.
+	Узнать, какие методы принадлежат интерфейсу.
+	Создать экземпляр класса, когда имя класса неизвестно до момента выполнения программы.
+	Получить и изменить значение поля по имени.
+	Вызвать метод объекта, зная только имя.
Минусы рефлексии:
-	Нарушения безопасности написанного кода и приложения в целом.
-	Происходит нарушение инкапсуляции из-за прямых обращений к private методам и переменным.
-	Производительность снижается, так как рефлексия в Java определяет типы динамически, сканируя classpath, чтобы найти класс для загрузки.
-	Сложность в поддержке кода, написанного с помощью рефлексии. Его довольно трудно читать, понимать и отлаживать.
================================ Аннотации:
С начала разработки на Java была необходимость помечать определенные классы или иерархии классов для выполнения тех или иных действий над ними. В далеком прошлом (до 2004 года, или до Java 5) это делали с помощью так называемых «маркерных интерфейсов».
Суть проста: 			создаём интерфейс без методов и имплементируем его в класс, который хотим пометить. Хороший пример оставшихся таких классов в Java — это: Serializable и Cloneable.
public interface Serializable {
}
Так выглядит маркерный интерфейс. Пометив свой класс таким интерфейсом мы получаем определённый функционал теми методами, которые работают с Serializable имплементирующими классами. На самом деле, внутри эта пометка нужна для реализации рефлексии для дальнейших нужд. Начиная с Java 5 такой механизм изжил себя и появилась возможность делать это с помощью новых сущностей — аннотаций. С появлением аннотаций, должна была исчезнуть потребность в использовании маркерных интерфейсов, но их используют в некоторых случаях до сих пор. Дело в том, что анализ аннотаций происходит уже во время исполнения кода, а некоторые ошибки важно выявить на этапе компиляции. Существуют стандартные аннотации в Java, которые встречаются довольно часто:
Аннотация		|		Описание
----------------------------------------------------
@Override		|	Отмечает метод, который переопределяет метод, объявленный в суперклассе или интерфейсе
@Deprecated		|	Помечает код как устаревший
@FunctionalInterface	|	Помечает интерфейс, имеющий всего один абстрактный метод
----------------------------------------------------------------------------------------
Пометка в виде аннотаций говорит о том, что этот класс, метод или поле наделён особенными свойствами. Аннотации большей частью работают «под капотом». Они во-первых, 		-помогают распознать особенную сущность (класс, поле или метод), 
во-вторых, 		-делают за нас некоторую работу с помощью рефлексии. 
Существуют целые библиотеки, которые с помощью аннотаций «под капотом» делают за нас определенную работу. Самая распространенная из них — Lombok.
-------------------------------- Lombok:
—это плагин (надстройка) компилятора, который с помощью ключевых слов (аннотаций) скрывает огромное количество кода. Тем самым он расширяет язык, добавляет функциональность и упрощает разработку. Рассмотрим несколько аннотаций, которые Lombok предлагает нам для использования. На сайте проекта:
https://projectlombok.org 			есть инструкция по использованию и описание всех существующих аннотаций.
Аннотация		|	Описание			|	Что делает
@ToString		|	@ToString
			|	public class MyClass		|	Генерирует реализацию для метода toString(), которая  состоит из представления объекта: имя класса, все поля и их значения.
@EqualsAndHashCode	|	Подробнее можно изучить 
			|	на сайте. Там же описан 
			|	пример с использованием 
			|	@EqualsAndHashCode и 
			|	без него со стандартной 
			|	реализацией 			|	Генерирует реализации equals и hashCode
@Getter / @Setter	| 	@Getter
			|	@Setter
			|	private String field = “field”;	| 	Генерирует геттеры и сеттеры для частных полей
@NonNull		|	public MyClass(@NonNull String nonNullField) {
			|	this.nonNullField = nonNullField
			|	}				|	Аннотацию @NonNull можно использовать для явного уточнения, что поля не должны являться null при создании экземпляра объекта, иначе выбросится исключение NullPointerException.
