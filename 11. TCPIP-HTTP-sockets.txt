================= Компьютерные сети:
Microsevices общаются между собой по сети.
Концентратора 	(hub, 	L1 OSI) 	—тот просто рассылает трафик всем подключённым устройствам (по всем портам). Многопортовый повторитель. Не используется. Заменены на switch;
Коммутатор 	(switch, L2 OSI)	-«переключает» каналы передачи данных и направляет их, по таблице коммутации, нужному получателю по порту. Виртуализированы.;

Маршрутизатора 	(router, L3 OSI)	—он связывает разные сети и работает с IP‑адресами. Требуется таблица MAC-адресов, - поскольку определять адреса соседей на уровне условно switch всё же надо.
Hub полезней switch - когда надо вычислить, кто загружает сеть. В этом случае хаб полезнее многих даже настраиваемых коммутаторов, которые не умеют в зеркалирование трафика.

================= Адресация сети. DNS:
DNS		Domain Name System в сети 	—это система доменных имён, которая преобразует человекочитаемые доменные имена в IP-адреса и обратно. DNS-имя не передается при отправке данных в каждом пакете, а служит лишь для преобразования символьного имени ресурса в IP-адрес.
A-запись 	Address Record в сети 		—это тип ресурсной записи, который связывает доменное имя с IP-адресом сервера. Базовый инструмент для перенаправления домена, подходит, если есть статический IP-адрес сервера и сервер настроен на обработку HTTP/HTTPS-запросов.
CNAME 		Canonical Name в сети		—это тип записи, которая указывает одно доменное имя на другое. Она работает как псевдоним, позволяя использовать разные имена для одного и того же сайта или сервера.
MX		Mail Exchange 			—тип DNS-записи, который указывает на почтовый сервер доменного имени. Это позволяет внешним почтовым серверам определять, куда отправлять электронную почту. 
dig -t A ya.ru		запросить А-запись домена
dig -t MX ya.ru		запросить MX-запись
dig -x 87.250.250.242	проверить IP-addr какому Domain они соответствуют. Это необходимо почтовой системе по SMTP (Simple Mail Transfer Protocol) — сетевой протокол для отправки и маршрутизации электронных сообщений между почтовыми серверами и клиентами, который при несовпадении ответов на запросы не считает адреса жоверенными и не принимает от них сообщения.
================== Особенности протокола TCP, сокеты:
TCP	с гарантией доставки. Протокол гарантирует:
	Установку соединения 		- перед началом обмена данными (так называемое «трёхэтапное рукопожатие» — three-way handshake):
		-Клиент отправляет серверу сегмент с флагом SYN (синхронизация).
		-Сервер отвечает сегментом с флагами SYN + ACK (подтверждение получения SYN).
		-Клиент подтверждает ответ сервера сегментом с флагом ACK. После этого соединение считается установленным.
	Целостность данных 		— информация доставляется без искажений. обработка ошибок, устранение дубликатов;
	Порядок доставки 		— пакеты приходят в той же последовательности, в которой были отправлены;
	Подтверждение получения		— отправитель ждёт подтверждения от получателя;
	Повторную отправку		— потерянных данных, если подтверждение не пришло, сегмент передаётся снова. Продублированный пакет будет отброшен получателем
	Управление потоком 		— скорость передачи регулируется так, чтобы получатель успевал обрабатывать данные (используется механизм «окна»). Меньшая скорость, чем в UDP, в некоторых случаях.
	Контроль перегрузки 		— протокол адаптирует скорость передачи в зависимости от состояния сети. это совокупность методов и алгоритмов, направленных на предотвращение перегрузки сетевой инфраструктуры при передаче данных. Основная задача защиты от перегрузки — обеспечить устойчивую и эффективную работу сети путём регулирования объёма передаваемых данных и поддержания баланса между скоростью передачи и доступной пропускной способностью канала.  Меньшая скорость, чем в UDP, в некоторых случаях.
UDP	без гарантии доставки;

================== HTTP протокол:
HTTP работает поверх TCP, но в HTTPv3 есть описание работы на UDP.
Протокол передачи гипертекста. Изначально HTTP создали для получения с серверов гипертекстовых документов в формате HTML. 
HTTP основан на технологии «клиент‑сервер»:
	Клиент 	(обычно веб‑браузер) 	инициирует соединение и отправляет запрос на сервер.
	Сервер 				ожидает запросов, обрабатывает их и возвращает ответ с результатом.
Обмен данными идёт по схеме «запрос‑ответ», в TCP API соединении.
Не сохраняет состояние (stateless). Протокол не «помнит» предыдущие запросы и ответы. Сохранение информации о состоянии обеспечивают дополнительные механизмы:
	куки (cookies) на стороне клиента;
	сессии на стороне сервера.
GET	запрос содержимого ресурса;
POST	передача пользовательских данных заданному ресурсу;
OPTIONS	получение информации о параметрах взаимодействия с целевым ресурсом. Этот метод позволяет клиенту (например, браузеру или API) узнать, какие методы и параметры доступны для конкретного ресурса, без выполнения каких-либо действий над ним.
Изменить протокол HTTP на другой в процессе работы с веб‑сервером можно — отправив сообщение с определёнными заголовками. Чаще всего меняют:
HTTP → HTTPS 			— самый распространённый сценарий (добавляется шифрование через TLS/SSL).
HTTP/1.1 → HTTP/2 или HTTP/3 	— обновление версии протокола для повышения производительности.
Реже 				— переход на специализированные протоколы (например, gRPC поверх HTTP/2).
----------------- URI Uniform Resource Identifier:
унифицированный идентификатор ресурса. Это последовательность символов, идентифицирующая абстрактный или физический ресурс: документ, изображение, файл, службу, ящик электронной почты и т. д.. URI может включать следующие компоненты: 
Схема (scheme) 				—показывает, как обращаться к ресурсу, чаще всего это сетевой протокол 	(http, ftp, ldap).
Иерархическая часть (hier-part) 	—данные, необходимые для идентификации ресурса 				(например, адрес сайта).
Запрос (query) 				—необязательные дополнительные данные ресурса 				(например, поисковой запрос).
Фрагмент (fragment) 			—необязательный компонент для идентификации вторичного ресурса ресурса 	(например, места на странице).
------------------ Headers:
это строки в HTTP-сообщении, содержащие разделённую двоеточием пару «имя-значение». Они сопровождают обмен данными между клиентом и сервером, передают информацию, которая не содержится в самом теле сообщения. Заголовки сообщают:
что просит клиент 		—тип данных, которые он может принять, язык;
что отправляет сервер 		—тип возвращаемых данных, их размер, статус обработки запроса;
как обрабатывать данные 	—нужно ли кэшировать, как долго хранить;
детали соединения 		—используемый протокол, настройки безопасности.
Request Headers			— Заголовки запросов. Направляются клиентом (браузером, мобильным приложением) в запросе к серверу, сообщают ему сведения о клиенте и его предпочтениях. Примеры: User-Agent (идентификатор браузера и ОС), Accept (какие типы данных клиент способен принять), Authorization (данные для доступа).
Response Headers		— Заголовки ответов. Направляются сервером в ответе клиенту, сообщают о статусе ответа, сервере и о возвращаемых данных. Примеры: Server (сведения о серверном ПО), Content-Type (тип данных в теле ответа), Set-Cookie (установка cookies на стороне клиента).
General Headers 		— Общие заголовки, включаются в любое сообщение. Применяются и в запросах, и в ответах, относятся ко всему сообщению в целом. Примеры: Date (дата/время создания), Cache-Control (директивы кэширования), Connection (параметры управления соединением).
Entity Headers			- Сопровождлаюь каждую сущность сообщения.
Заголовки для управления кэшированием — особая группа, часто включающая заголовки из других категорий (например, Cache-Control, Expires в ответах или If-Modified-Since в запросах). Их задача — указать браузеру или промежуточным прокси, можно ли сохранять копию ресурса локально и как долго её считать актуальной.
------------------ Content Negotiation:
Механизм протокола HTTP, позволяющий обслуживать разные версии ресурса с одним URI. Клиент указывает, какая версия ему подходит лучше всего, а сервер выбирает оптимальное представление. 
Механизм автоматического определения необходимосно ресурса. Методы согласования:
1. Согласование, управляемое сервером 	(Server-driven Negotiation)	Сервер самостоятельно выбирает наилучшее представление на основе заголовков запроса клиента.
2. Согласование, управляемое агентом 	(Agent-driven Negotiation)	Клиент выбирает из списка доступных ресурсов, который предоставляет сервер.
3. Прозрачное согласование 		(Transparent Negotiation) 	Комбинация двух предыдущих методов, где кэш выполняет согласование под управлением сервера для последующих запросов.
Заголовки для согласования (управляемое сервером)
Accept 		:—указывает типы MIME, которые может обработать клиент:
		Accept: application/json, text/html; q=0.8
		application/json — приоритет 1.0 (по умолчанию);
		text/html — приоритет 0.8 (указан через q).
Accept-Charset 	:—кодировка символов:
		Accept-Charset: UTF-8, ISO-8859-1; q=0.7
Accept-Encoding :—поддерживаемые кодировки сжатия:
		Accept-Encoding: gzip, deflate, br
		Возможные значения: gzip, deflate, br (Brotli), compress, zstd, identity.
Accept-Language	:—предпочитаемый язык:
		Accept-Language: en-US, en-GB; q=0.9, ru; q=0.8
User-Agent 	:—информация о клиенте (браузере, ОС), помогающая серверу адаптировать ответ.
Vary		:—заголовок ответа, указывающий, по каким параметрам может варьироваться содержимое:
		Vary: Accept-Encoding, Accept-Language
----------------- Cookie (HTTP-cookie, WEB-cookie):
-механизм сохранения части информации у пользователя (Клиента), чтобы, после, к ним обращаться. 
-небольшой фрагмент данных, который веб‑сервер отправляет браузеру пользователя. Браузер сохраняет эти данные и возвращает их на сервер с каждым последующим HTTP‑запросом к тому же сайту. Это позволяет серверу «запомнить» пользователя между запросами — несмотря на то, что сам протокол HTTP не хранит состояние (stateless).
	1/	Установка куки. При получении HTTP‑запроса сервер может отправить в ответе заголовок Set-Cookie. Например:
		HTTP/1.0 200 OK
		Content-type: text/html
		Set-Cookie: yummy_cookie=choco
		Set-Cookie: tasty_cookie=strawberry
	2/	Сохранение куки. Браузер получает этот заголовок и сохраняет указанные куки на устройстве пользователя.
	3/	Отправка куки. При следующих запросах к тому же серверу браузер автоматически добавляет сохранённые куки в заголовок Cookie:
		GET /sample_page.html HTTP/1.1
		Host: www.example.org
		Cookie: yummy_cookie=choco; tasty_cookie=strawberry
Основные виды куки. По принадлежности:
First‑party cookies (основные) 		— устанавливаются непосредственно посещаемым сайтом и ограничены его доменом.
Third‑party cookies (сторонние) 		— создаются другими сайтами (например, рекламными баннерами). Часто используются для трекинга и показа таргетированной рекламы.
По времени жизни:
Сессионные (session cookies) 		— существуют только в течение текущей сессии браузера и удаляются при его закрытии (если не включено восстановление сессии).
Постоянные (persistent cookies) 	— хранятся до указанной даты (Expires) или в течение заданного интервала (Max-Age).
По безопасности:
Secure cookies 				— передаются только по HTTPS (защищённым соединениям).
HttpOnly cookies 			— недоступны из JavaScript (document.cookie), что защищает от атак типа XSS (межсайтовый скриптинг).
Для чего используются куки
Управление сессиями: 	авторизация (логины, пароли)/ корзины покупок/ прогресс в формах.
Персонализация: 	сохранение пользовательских настроек (язык, тема, регион).
Отслеживание (трекинг):	сбор статистики о поведении пользователя/ история посещений/ клики.
Реклама: 		показ релевантных объявлений на основе интересов пользователя.
================== WebSocket:
-независимый веб‑протокол для создания интерактивного соединения между сервером и клиентом (обычно браузером) с возможностью обмена сообщениями в режиме реального времени.
-хорош для динамических приложений, - приложения, которые генерируют или изменяют свой контент в реальном времени в зависимости от действий пользователя, системных событий, данных из баз данных или других внешних факторов. В отличие от статических приложений, где содержимое остаётся неизменным для всех пользователей, динамические приложения адаптируются и обновляются в процессе работ.
-нет обратной совместимости с HTTP. Сменить протокл на HTTP не получится.
	1/	Установление соединения («рукопожатие», handshake). Клиент отправляет HTTP‑запрос с заголовком Upgrade, сигнализирующим о желании перейти на протокол WebSocket. 
		GET /demo HTTP/1.1
		Upgrade: WebSocket
		Connection: Upgrade
		Host: site.com
		Origin: http://site.com
	2/	Ответ сервера. Если сервер поддерживает WebSocket, он отвечает кодом 101 Switching Protocols и подтверждает переход. 
		HTTP/1.1 101 Web Socket Protocol Handshake
		Upgrade: WebSocket
		Connection: Upgrade
		WebSocket-Origin: http://site.com
		WebSocket-Location: ws://site.com/demo
	3/	Обмен данными. После успешного «рукопожатия» устанавливается постоянное двунаправленное соединение. Данные передаются в обе стороны без дополнительных запросов — сервер может отправлять информацию клиенту в любой момент.
